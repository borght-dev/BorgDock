BorgDock — Stability & Speed Plan

2026-09-02 · target: master @ 88f4e69c (2.0.0) · scope: the seven complaints that make BorgDock unused today, plus the account, provider and T3 Code extensions added the same day (sections H–K)

One-paragraph summary. Almost every complaint traces to a small number of structural mistakes rather than many small bugs: (1) about 35 Rust commands are synchronous and therefore run on the GUI thread, including SQLite writes of multi-megabyte ETag blobs every poll cycle and subprocess spawns; (2) the Agent Overview feature bootstraps, binds a port, opens a third WebView2 window and writes into your repos on every launch, and in some states re-reads whole Claude transcripts once per second; (3) the main window polls the heavy worktree scan every 30 s, which on this machine is ~24 s of sequential git per cycle; (4) the setup-wizard command shrinks the main window to 520×640 on every boot because its effect fires before settings hydrate; (5) the SQL window's CodeMirror styles are blocked by Tauri's CSP nonce injection; (6) the Focus scorer gives zero points to "commented" reviews and to your own green PRs. Fixing these is roughly eight PR-sized changes, ordered below so the crash/hang fixes land first. Four more PRs (9–12) cover the additions from later the same day: a GitHub account per repo, replacing the Claude API section with headless claude -p / codex exec, a provider abstraction that adds Codex, and launching sessions into T3 Code instead of a terminal.

A. Hangs and crashes

A1. Sync commands execute on the GUI thread ✔ verified in source

CLAUDE.md line 86 states that Tauri 2 runs sync and async commands on a worker thread. The source says otherwise: tauri-macros/src/command/wrapper.rs:264 marks non-async commands as blocking, and tauri-2.11.5/src/ipc/mod.rs:326,371 only spawns for the async path. On Windows both wry IPC entry points (WebResourceRequested for the custom protocol and WebMessageReceived for postMessage) fire on the UI thread. Sync commands therefore run inline on the main thread.

Commands doing blocking work there today:

CommandFileBlocking work
cache_save_etags / cache_save_prs / cache_load_etags / cache_load_prs / cache_initsrc-tauri/src/cache/mod.rs:18–441SQLite. cache_save_etags runs every poll with up to 500 entries each carrying a full response body (client.ts:66–75, useGitHubPolling.ts:157). No dirty tracking; every row is re-serialised and INSERT OR REPLACEd.
load_settings / save_settingssettings/mod.rs:148,228File read + parse; migrate_credentials_to_keychain touches Windows Credential Manager on every load.
gh_cli_token, az_cli_available, get_system_theme, open_log_folderauth/mod.rs:5, auth/ado.rs:167, platform/theme.rs:1, platform/logs.rs:20Subprocess spawns (200–3000 ms cold on Windows, per the repo's own comments).
focus_session_paneagent_overview/commands.rs:138 → platform/focus_pane.rs:48sysinfo refresh of every process on the machine with cwd, then canonicalize per process. Multi-second hard freeze on click.

Because every run_on_main_thread + oneshot in this repo, every tauri getter! (outer_size, theme, …) and tray.set_icon are untimed waits on the main thread, one stalled sync command turns into "every invoke hangs, splash never progresses".

A2. Detached repaint thread with a blocking getter

platform/window.rs:451–456 spawns an OS thread, sleeps 250 ms, calls set_focus() and force_repaint, which calls outer_size() (a blocking getter) from a non-UI thread. hotkey.rs:313–319 documents that this exact pattern "saturated WebView2's PostMessage queue and hard-crashed the process" and removed it from palette_ready. It survives in open_pr_detail_window.

A3. wry null-pointer panic in parent_subclass_proc

The May panic dereferenced a destroyed ICoreWebView2Controller during WM_SIZE. wry 0.55.1 still has the same subclass proc. Mitigations on our side: never destroy and recreate pop-out windows with the same label in quick succession, prefer hide/show for palettes (already done for worktree palette, not for pr-detail/settings/whats-new), and pin to the newest wry once its fix lands. Also make the panic hook safe: lib.rs:75 logs via the Webview target inside the hook, which can re-enter and abort.

A4. Zombie process on relaunch

tauri_plugin_single_instance::init(|_app, _args, _cwd| {}) is a no-op; the second instance proceeds, fails to bind the port and hotkeys, and fails to create a webview. Wire the callback to show_or_focus_main and make the new instance exit. Separately add a clean-exit path: uninstall the mouse hook (click_outside.rs is never uninstalled at exit if the flyout is visible), flush geometry, stop the OTLP server.

A5. Panics reachable in normal use

  • agent_overview/settings_merge.rs:195,199 .expect("settings root must be an object") and .unwrap() on env — runs at startup against every active repo's .claude/settings.json.
  • Poisoned-mutex .lock().unwrap() in file_palette/cache.rs:111,120, file_palette/content_search.rs, git/diff.rs — one panic permanently breaks the file palette for the session.
  • WH_MOUSE_LL hook proc in click_outside.rs:53–107 takes a mutex and does work; Windows silently unhooks after 300 ms.

A6. Things that are fine

All git/*, file_palette/* and SQL commands already use spawn_blocking; SQL isolates tiberius panics; PollingManager is a clean timeout chain; all listen()s and intervals have cleanups; no lock is held across an .await; no block_on.

B. Agent Overview (unused, expensive)

Footprint: ~3,990 LOC Rust + ~4,280 LOC TS, exclusive deps axum, glob, sysinfo (and tower is already dead). Default settings are enabled: true, auto_open_on_startup: true (settings/models.rs:530–539), and your settings file has both on.

What it does on every launch

  1. bootstrap_known_sessions + bootstrap_from_jsonl glob ~/.claude/projects/*/*.jsonl and read_to_string every recent transcript to inspect 30 lines (bootstrap.rs:187). This runs before the enabled check (lib.rs:216–255).
  2. Binds TCP 4318 (falls through to 4327).
  3. sync_active_project_settings rewrites <repo>/.claude/settings.json in your worktrees and drops a .bak.<epoch> file each time (settings_merge.rs:174–184).
  4. Opens a third WebView2 window (~60–120 MB).
  5. Starts a 1 Hz tick that, for any session in Awaiting/Finished whose last message could not be extracted, re-reads and fully JSON-parses the whole transcript every second forever (lib.rs:354–368, cwd_resolver.rs:194–199). Blocking fs on the shared tokio runtime, so it adds latency to unrelated async commands.

Plan

  • Flip defaults to off; gate bootstrap, OTLP, settings sync, tick loop, hotkey Ctrl+Super+Shift+A, tray item and auto-open on enabled.
  • Fix the tick loop regardless (sentinel for "no text", bounded tail read, spawn_blocking).
  • Put the module behind a Cargo feature agent-overview (default off) and a Vite entry toggle, so it can be removed cleanly later without touching the rest. Stop writing into repos entirely; if the feature is on, write only ~/.claude/settings.json and only when the values changed.

D. Wrong window size until you drag an edge

Root cause, verified in code. src/App.tsx:83–108:

const needsSetup = forceWizardFromUrl || !settings.setupComplete || settings.repos.length === 0 || (...pat...);
useEffect(() => { if (needsSetup) invoke('show_setup_wizard'); }, [needsSetup]);   // not gated on !isLoading

On mount, settings are still defaults (setupComplete: false), so needsSetup is true and the effect fires every launch. platform/window.rs:328–356 then resizes the main window to 520×640 logical (780×960 physical at your 150 %) and shows it. When settings hydrate, needsSetup flips to false but the effect body only acts when true. The render path is gated (App.tsx:293), so you see the real UI squeezed into a wizard-sized window. Dragging an edge makes tao apply min_inner_size 1200×720 logical = 1800×1080 physical, the "snap". The Resized listener also persists the wizard size, which is why the log shows 535×649 being clamped up every launch.

Two adjacent facts: nothing in the main entry calls window_ready (the comment at lib.rs:420–423 is stale), so show_setup_wizard is currently the only thing that shows main at startup; and ui.startMinimizedToTray is declared and toggled but read by nothing.

Fix

  1. Gate the effect on !isLoading (and on a hasLoaded flag from the settings store).
  2. Add an explicit reveal: main calls window_ready after settings hydrate; window_ready honours startMinimizedToTray.
  3. show_setup_wizard should not resize main. Open the wizard in its own window (pattern exists: settings window) or restore saved geometry on completion.
  4. In window_geometry.rs set position before size so a mixed-DPI move does not misconvert, and do not persist sizes below the kind's minimum.

E. SQL editor line numbers stacked / wrong font

Root cause, verified. The editor is CodeMirror 6 (src/components/sql/SqlEditor.tsx:249–303); its base theme (flex row of gutter + content, monospace, line-height) is injected at runtime by style-mod as a nonce-less <style>. sql.html contains an inline <style>; tauri-utils inject_nonce_token adds a nonce to it and Tauri appends 'nonce-…' to style-src. Per CSP3, a nonce in the directive makes 'unsafe-inline' ignored, so CodeMirror's injected sheet is refused. Packaged builds only; dev server and Storybook have no CSP, which is why no test caught it. SqlApp.test.tsx mocks the editor out entirely.

Fix

  1. In SqlEditor.tsx read the nonce from the injected inline style tag (document.querySelector('style[nonce]')?.nonce) and pass EditorView.cspNonce.of(nonce).
  2. Move the html, body, #root rules from all 12 HTML entries into src/styles/index.css so no inline styles remain to nonce (index.html's inline splash markup can keep its CSS as a class in the stylesheet).
  3. Add a Playwright e2e that runs against the packaged build (or at least a vitest asserting .cm-scroller computed display: flex with a simulated CSP) so it cannot regress silently.
  4. Drop the redundant inline pixel height in SqlEditor.tsx:332; the parent already sizes it.

F. Worktree overview: slow, unsorted, cold

Why it is slow

  • useWorktreeMap (main window) runs heavy list_worktrees every 30 s: 1 + 3N sequential git processes (status, rev-list, rev-parse per worktree) — measured 24.1 s for the 14 FSP-Horizon worktrees. It uses only path + branch, which the bare command returns in ~0.2 s. git status without --no-optional-locks also writes the index in every worktree each cycle.
  • The palette stays invisible until load_settings (sync, main thread) → per-repo list_worktrees_bare → 50 ms timer → window_ready round-trip (WorktreePaletteApp.tsx:264–336). Then it auto-resizes after reveal (visible jump).
  • First Ctrl+F7 builds a new WebView2 (~350–520 ms in the log) plus ~240 KB JS + 134 KB CSS.
  • No cache anywhere; second opens only feel faster because stale rows are not cleared.
  • Git is resolved via PATH on every spawn; no timeouts on .output().

Why it is unsorted

WorktreePaletteApp.tsx:409–419 sorts repo → main first → favorites first → branch name. The visible secondary line is the folder name (worktree1…worktree9), 11 favorites are hoisted, and localeCompare without numeric puts worktree10 before worktree2.

Plan

  1. New src-tauri/src/git/worktree_cache.rs modelled on platform/flyout_cache.rs: Tauri-managed state, worktree_cache_get_all (instant) and worktree_cache_refresh (per-repo concurrent spawn_blocking, sorted, emits worktrees-updated to all windows). Refresh at startup, on palette open, on create/remove/prune, and on a slow timer (5 min).
  2. Palette: render from cache on mount, reveal immediately (skeleton if empty), revalidate in the background; settings (favorites) load in parallel and only gate the star, not the list.
  3. Main window's useWorktreeMap subscribes to the same cache/event. No timer.
  4. Sort: repo → main pinned → folder name with { numeric: true, sensitivity: 'base' }; favorites shown as a star, not hoisted (or an explicit "favorites first" toggle).
  5. Harden git/worktree.rs: parallelise the heavy variant (for the checkout panel that does need it), --no-optional-locks, cache the resolved git.exe path in a OnceLock, add a wall-clock timeout.
  6. Optional: pre-create the palette hidden at startup behind ui.prewarmWorktreePalette; open_or_toggle_palette already handles the exists-but-hidden path.

H. Two GitHub accounts on one machine

Situation. gh auth status on this laptop shows two logins on github.com: KvanderBorght_gomocha (active) and borght-dev. BorgDock's gh_cli_token (src-tauri/src/auth/mod.rs:5) runs plain gh auth token, which returns only the active account's token. borght-dev/BorgDock is public, but the enterprise token still cannot resolve it through GraphQL because the enterprise account lives in a managed enterprise (EMU-style login with the _gomocha suffix), which is walled off from repos outside the enterprise. Adding the enterprise login as a collaborator on your personal repo is therefore not possible, and the personal token cannot see Gomocha-FSP.

Can it be solved on the machine alone? Only partially. Switching the active gh account fixes one repo and breaks the other. What does work locally, verified today, is gh auth token --user borght-dev and gh auth token --user KvanderBorght_gomocha: both return a 40-character token without switching the active account. BorgDock just needs to ask for the right one per repo.

Design

  • RepoSettings (src/types/settings.ts:15) gets githubAccount?: string (a login). Empty means "active gh account" for backwards compatibility.
  • gh_cli_token takes an optional user and passes --user <login>. The settings UI lists accounts by parsing gh auth status (or gh api user per token) and shows an account picker per repo, with a "Detect" button that tries each account against the repo and picks the one that resolves it.
  • Frontend: getGitHubToken becomes keyed by account; GitHubClient becomes one instance per account (Map<login, GitHubClient>), with polling, ETags and rate limits tracked per client. The status bar shows the tighter of the per-account pools with its login.
  • Repo owner validation in the settings form: reject anything that is not [A-Za-z0-9-]+, and offer to parse git remote get-url origin (including SSH aliases such as git@github-borghtdev:borght-dev/BorgDock) into owner/name. That is how the current bad owner got in.
  • PAT mode: allow a PAT per repo the same way (stored under a per-account keychain entry).

K. T3 Code as the session launcher

What was verified on this machine. T3 Code (Alpha) 0.0.38 is installed via winget and running. Its server listens on http://127.0.0.1:3773, published in ~/.t3/userdata/server-runtime.json. Clients use Effect RPC over WebSocket at /ws, but there is also a plain HTTP surface: POST /api/orchestration/dispatch (a ClientOrchestrationCommand), GET /api/orchestration/threads/:threadId, and auth routes POST /oauth/token (RFC 8693 token exchange of a one-time pairing credential for a Bearer access token), POST /api/auth/websocket-ticket, POST /api/auth/pairing-token. Scopes include orchestration:read and orchestration:operate. The CLI (npx t3) has project add <path>, pair, serve, auth but no thread subcommand. The desktop app registers the t3code:// scheme but only t3code://app is used; its activation contract is open-workspace { workspaceRoot } → { projectId, threadId }, which is what launching the executable with a folder does.

Command payloads (from packages/contracts/src/orchestration.ts on main; the local install's thread.created events match):

project.create      { type, commandId, projectId, title, workspaceRoot, createWorkspaceRootIfMissing?, createdAt }
thread.create       { type, commandId, threadId, projectId, title, modelSelection: { instanceId, model, options? },
                      runtimeMode: "approval-required"|"auto-accept-edits"|"auto"|"full-access",
                      interactionMode: "default"|"plan", branch: string|null, worktreePath: string|null, createdAt }
thread.turn.start   { type, commandId, threadId, message: { messageId, role: "user", text, attachments: [] },
                      modelSelection?, titleSeed?, runtimeMode, interactionMode, createdAt }
RPC only:           git.preparePullRequestThread { cwd, reference, mode: "local"|"worktree", threadId? }
                    → { pullRequest, branch, worktreePath }

Provider instances configured in your T3 settings: codex, claudeAgent ("Claude Gomocha"), claudeAgent_outlook (personal Claude home). Your T3 projects already include E:\BorgDock\src\BorgDock.Tauri and several D:\FSP-Horizon\.worktrees\worktreeN folders. The local database ~/.t3/userdata/state.sqlite has projection_threads with project_id, title, branch, worktree_path, model_selection_json, linked_pull_request_json, pending_approval_count, pending_user_input_count, settled_at, unsettled_at, and projection_projects with workspace_root. Reading it in mode=ro while T3 runs is safe (WAL).

Integration design, three tiers

  1. Tier 1, no auth, ships first. "Open in T3 Code": t3 project add <worktree> if the workspace root is unknown (check the projection table), then launch "T3 Code (Alpha).exe" <worktree>, which activates open-workspace and lands you in a new thread for that project. The prompt goes to the clipboard and a toast says "prompt copied, paste to start". Ugly but works today and needs nothing from T3.
  2. Tier 2, paired client, the target. One-time pairing: BorgDock runs npx t3 pair --ttl 5m (or the user pastes a pairing token), exchanges it at POST /oauth/token with grant_type=urn:ietf:params:oauth:grant-type:token-exchange and subject_token_type=urn:t3:params:oauth:token-type:environment-bootstrap, stores the Bearer token in the keychain, and re-pairs when GET /api/auth/session says expired. Then "Fix with T3" is: ensure project (dispatch project.create with our worktree as workspaceRoot, or reuse the existing project id from the projection), dispatch thread.create with branch and worktreePath set to the PR branch and worktree BorgDock created, modelSelection from a BorgDock setting mirroring T3's instance ids, runtimeMode from a setting (default auto-accept-edits), then dispatch thread.turn.start with the prompt as message.text and the PR title as titleSeed. Finally bring T3 to front. The desktop app updates live through its own subscription, so the thread appears immediately.
  3. Tier 3, replace Agent Overview. A "Sessions" strip on each PR card and in the PR detail Overview tab lists T3 threads whose worktree_path or branch matches, with status (running, waiting for approval, waiting for input, settled) from the projection tables, polled cheaply from SQLite (or via orchestration.subscribeShell over the WebSocket once the client exists). Clicking focuses that thread in T3 (Tier 1 activation plus thread id, or the RPC equivalent). This gives you the "who is waiting on me" signal the Agent Overview tried to provide, without OTLP, transcript parsing or repo writes.

Risks and mitigations

  • T3 is alpha; contracts change. Pin the tested T3 version in a constant, probe server.probe / GET /api/auth/session at startup, and degrade to Tier 1 when the dispatch route rejects the payload. Log the server version in our log.
  • HTTP dispatch versus WebSocket: dispatch over HTTP is enough for create + first turn. Only Tier 3's live status and git.preparePullRequestThread need the WebSocket client. Reuse T3's own worktree creation (mode: "worktree") only once the WS client exists; until then BorgDock keeps creating worktrees itself, which it already does.
  • Pairing is a manual step once; without it, Tier 1 still works.
  • Token storage in the Windows keychain via the existing keychain.rs, async after PR1.
