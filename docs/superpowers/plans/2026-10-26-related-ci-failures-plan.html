Related CI failures

2026-10-26 · issue #90 · baseline master @ 3f0964d2 (4.6.0) · scope: the full feature, not the MVP in the issue. Paths are relative to src/BorgDock.Tauri/ unless they start with /.

Summary. BorgDock already sees every failed check of every open PR on each poll. It throws that away. The GraphQL rollup carries job ids, then contextToCheckRunLite sets id: 0 and keeps only names. This feature keeps the identity of every failed job attempt and reads a bounded, sanitized piece of evidence for each one: job metadata, annotations and the tail of its log. It fingerprints the failure and groups equal fingerprints across PRs and the default branch. Each group gets a confidence with its reasons, a hypothesis (infrastructure, base branch, flaky, branch-specific) and one explicit owner. The owner is a T3 thread, a terminal session, you, or a GitHub tracking issue. Every agent launch on a grouped failure checks the owner first. Grouping only advises: it never changes what checks say, never reruns anything on its own and never edits a PR.

Along the way it fixes three things that are wrong today. The first-failure excerpt downloads the whole job log through the webview with no byte cap, its timeout ends when headers arrive, and the CSP's connect-src doesn't allow the blob host GitHub redirects logs to (so it probably fails in packaged builds). Fix prompts never receive the parsed errors: every caller passes errors=[] and rawLog=''. And nothing stops two agents from chasing the same failure.

The card sits above the grouped view in the main panel and above the flat list in the pop-out. It lists the groups the PR's current failed jobs belong to. Details expands in place:

  • Occurrences. One row per job attempt: PR (or master), workflow and job, matrix values, attempt, tested SHA linked to the commit, when, conclusion, a required badge, and links to the job and the run. Older attempts stay as rows. A later pass shows as "passed on attempt 2", it doesn't remove the row.
  • Why these match. The confidence reasons as sentences: "Same test", "Same assertion, Expected 200 / Received 503", "Same failed step Run e2e", "3 matrix values", "Different PR heads, no shared changed files".
  • Evidence. The sanitized excerpt of one representative occurrence, with a picker for the others. Truncated logs say "read the last 2 MiB of 31 MiB".
  • Hypothesis. A select with the computed hypothesis marked "suggested" and its reasons. Choosing one stores a human classification.
  • History. First observed (worded "earliest seen by BorgDock", never "first occurrence"), claims, overrides, fix PR, merges and splits.
  • Menu. Merge with another group, split an occurrence out, mark resolved, track on GitHub, copy a sanitized summary.

3.2 PR list

  • Show 4 PRs sets a group filter in the main window's PR list. A dismissible chip in the toolbar reads "Related failure: checkout 503 · 4 PRs ×". It combines with search and the segmented filter, and it is session state like the rest.
  • From the pop-out, the button emits to the main window (same route showPr uses), which switches to PRs and applies the filter.
  • Failing rows that belong to a confident shared group get a small "shared · 4" marker next to the check bar, with the group title in its tooltip. The row's primary chip does not change.

3.3 Focus card

CiFailuresFocusCard sits next to the Dispatch card and hides when empty. It lists groups that affect at least one of your PRs and have no owner, owners that went stale, and fixes that merged with PRs still red. Each row has one primary action: Investigate…, Still on it? or Rerun affected….

3.4 Launch guard

Fix, Open in T3 and Investigate all ask the guard first. If a failed job of this PR is in a group with an active owner:

Already being investigated
  checkout 503 · 4 PRs · owner: T3 "CI: checkout 503" (running, 2 h)

  [Open the owner]   [Send this PR to the owner]   [Launch anyway]   Cancel

Send this PR to the owner posts a short message to the owning T3 thread with the PR, job link and excerpt. Launch anyway records an override in the group's history. If the group is shared but unowned, Fix offers "Investigate the group instead" next to "Fix in this PR only", because a fix in one branch is the wrong move for a broken master.

3.5 Settings, maintenance, notifications

  • GitHub → Related CI failures. Collect evidence, include default branch, cross-repo suggestions, retention days, log tail size, per-log timeout, daily evidence limit, owner lease hours. One usage line: "Today: 42 evidence reads, 18 MiB, 3 skipped by the limit."
  • Notifications. A group reaches N PRs and is unowned (N defaults to 3), an owner goes stale, a fix merged and affected PRs are still red. All off for the first full read of every source, like Dispatch's everySourceRead.
  • Maintenance. "Clear CI failure history" (keeps manual decisions, releases claims with an event) and "Manual decisions (N)" with remove. Clearing the PR cache leaves CI history alone.

Two SHAs, always. For pull_request events the job's head_sha is the PR head while the run tested the synthetic merge commit. For merge_group it is the merge-group commit. The UI shows the tested SHA and marks an occurrence "outdated" once the PR head moves past it. Fingerprints never include SHAs.

Matrix values. The API has no structured matrix. The default job name suffix build (18.x, ubuntu-latest) is parsed into values when present, and the base name is the job identity. A custom name: without a suffix yields no values. This is a heuristic and the detail view labels it as such.

5.1 Observe

  • Extend CHECK_CONTEXT_FIELDS with completedAt and workflowRun { databaseId runNumber }. In mapNode, put a compact ciJobs list on PullRequestWithChecks: for each latest Actions context, its job id, run id, name, workflow name, event, conclusion and completed time. Non-Actions failures keep their check run id or status context name.
  • The CI runtime subscribes to accepted poll results (the same point dispatch-sync uses), never to renders. A failed job id it hasn't seen becomes a pending occurrence. A known failed occurrence whose job name now passes in the same run becomes passed_on_retry. A pass on a new run becomes passed_after_push.
  • When the first sighting is attempt N > 1 and earlier attempts are unknown, one call to actions/runs/{id}/attempts/{n-1}/jobs backfills them. Polls are a minute apart, so a fast rerun can hide an attempt otherwise.
  • Default branch (D3). Every 5 minutes per repo, actions/runs?branch={default}&event=push&per_page=20 with the client's ETag cache (a 304 doesn't count against the rate limit). New failed runs or attempts list their jobs once. The latest pass per workflow path is kept too, so "fixed on master" can be stated.
  • First run. Current failures are recorded as observations, and their evidence is queued like any new failure. History is never backfilled at startup.

5.2 Queue and budget

  • Priority: your PRs, then PRs that need your review, then the rest, then default-branch runs. Newest first inside each band.
  • Per account: at most 2 evidence reads at once, 300 a day (the usage table counts them, so the limit survives restarts). Skips are counted and shown, never silent.
  • Backoff on 403/429 with Retry-After. Pause the queue when the client's REST remaining drops below 10% of its limit.
  • Each read runs inside withAccountRequest and holds the slot until the Rust call returns, including the body. That closes today's early-release gap for this path.
  • Every queued item carries the runtime generation. A reply from a previous generation (account changed, repo removed) is dropped before it touches the store.

5.4 Extract (Rust)

  • Port every parser in log-parser.ts with its tests as fixtures, and add structure the fingerprints need: test id and parameters, error class, expected/actual pairs, top application stack frames.
  • New parsers for what the configured repos run: Vitest/Jest (FAIL file > suite > test, AssertionError), xUnit/NUnit assertion blocks (Assert.Equal() Failure, Expected/Actual), cargo test (---- name stdout ----, panicked at), npm/bun install errors (npm ERR! code E404), Docker build steps. Add pytest and Go only if a configured repo needs them.
  • The failed step from job metadata narrows extraction: the section from that step's ##[group] header to the end of the tail wins over earlier noise. When the header can't be found, the whole tail is used and the reason says so.
  • Playwright retries of the same test inside one job collapse into one signal with a retry count.

6. Fingerprints and confidence

Rust returns sanitized but unnormalized fields. Normalizing, fingerprinting, tiering and assignment are pure TypeScript in services/ci-failures/, in the style of the Dispatch engine. Stored signals keep the sanitized fields, so a new fingerprint version re-runs over the database without any log.

6.5 Assignment, merges and upgrades

  • Groups own fingerprints (group_fingerprints). A new fingerprint gets a new group, unless a must_link decision ties it to an owned one.
  • Merge moves the fingerprints to the older group and leaves merged_into on the other, so links and claims follow. When both groups have active claims, the merge asks which owner stays and releases the other with an event.
  • Split writes a cannot_link and moves the fingerprint to a new group.
  • A fingerprint version bump re-fingerprints stored signals in one transaction. Each new fingerprint goes to the group that held most of its old members. Decisions are rewritten through the same mapping. A decision that maps ambiguously is kept and flagged in Maintenance, never dropped.
  • A group is shown as related when it spans 2 or more PRs, or 1 PR plus the default branch, or one job that failed on 2 or more attempts. Single-occurrence groups are stored and stay hidden.

A settled T3 owner doesn't release itself. The card asks "Investigation finished?" with Resolved, Release and Keep, and offers the thread's PR as the fix PR.

8.2 Atomic claims

  • ci_claim(groupId, owner, expectedRevision) runs in one SQLite transaction. The unique partial index on active and stale claims per group lets one claimant win. The loser gets AlreadyClaimed { claim } and sees the guard dialog. This covers two windows, or a double click.
  • The launch flow claims before launching, with owner ref pending:{uuid}. On success it swaps in the scoped thread id (compare-and-set on revision). On failure it releases with a launch_failed event. If the release also fails, the claim stays launch_failed and visible.
  • Only one BorgDock install writes a given database. Claims don't coordinate between machines unless a group is tracked on GitHub (D1). The claim card says "this machine" or "tracked in #123" so you know which guarantee applies.

9. Investigations, fixes and reruns

9.1 Investigate sheet (D2)

  • Extract launchInSlot({slot, model, effort, title, prompt}) from startThread/startRun in dispatch/launch.ts. All three callers use it.
  • InvestigateSheet reuses LaunchChoice (slot and model picker). The slot defaults to the T3 project whose workspace matches the group's repository.
  • Explicit evidence selection. A checklist of occurrences and excerpts that go into the first message, all sanitized, with a character count against the 20,000 prompt limit. Nothing goes in that you didn't see.
  • The prompt (investigationPrompt, editable) lists the occurrences with links, hypothesis and reasons, the required-check rule, and asks the agent to put BorgDock-CI-Group: {shortId} in any fix PR body.
  • The thread is linked to no work item (linkThread(id, null), as runs are) and titled CI: {group title}. Its claim stores the scoped id.
  • Terminal fallback, when T3 isn't paired or you pick it: launchAgentSession with the same prompt, in the default-branch worktree or else the earliest affected PR's. Owner kind terminal, lease-based.
  • Link existing thread: pick from Dispatch threads or local sessions on an affected branch.

9.2 Fix tracking

  • A fix PR is linked by hand, suggested from the owner thread's pullRequests, or found by its BorgDock-CI-Group body line in the poll (the body is already in the hot query).
  • When the fix PR merges, the group shows "Fix merged" and the Focus card lists PRs still red in it.
  • New occurrences after the fix merged and reached the default branch reopen the group with "Seen again after the fix".
  • Seven days without a new occurrence moves a group to quiet. Only you resolve it.

9.3 Rerun affected (confirmed, never automatic)

The sheet lists each affected open PR, the workflow runs that would get rerun-failed-jobs (which reruns every failed job in that run, and the sheet says so) and required badges. Then you confirm. It calls the existing rerunFailedChecks one PR at a time inside the budget and reports per PR.

A rerun reuses the original commit and ref. For a pull_request run that is the old merge commit, so a rerun never picks up a fix that landed on master. The sheet adapts to the classification. For infrastructure and flaky groups it offers the rerun. For base-branch groups it says the branch needs updating and links each PR, without updating anything itself.

9.4 Agent-assisted compare

On a candidate, Ask an agent sends the two sanitized excerpts and fingerprints through run_headless_prompt and expects {"same": bool, "reason": string}. The answer shows as a suggestion with Accept (writes must_link) and Reject (writes cannot_link). It never writes a decision itself. Before sending, the request shows exactly what goes out.

9.5 Shared ownership on GitHub (D1)

  • Track on GitHub opens a preview of the issue: title, sanitized summary, affected PRs as links, a <!-- borgdock:ci-group v1 {fingerprint hashes} --> marker (hashes only), label borgdock-ci-failure, assignee you. Nothing posts until you confirm.
  • Every 10 minutes, each repo's open issues with that label are listed (ETag cached). A marker that matches a local group links the issue and shows its assignee as owner, so another machine or a teammate sees the claim.
  • Update issue (explicit) comments the new affected PRs. Close issue is offered when you resolve the group. BorgDock never writes to the issue on its own.
  • If the label can't be created (permissions), the issue is created without it and discovery falls back to searching the marker text.

9.6 Notifications and digest events

  • services/ci-failures/events.ts emits CiFailureEvent envelopes after each durable write: group-formed, group-grew, owner-stale, fix-merged, seen-after-fix, resolved. The id is {groupId}:{kind}:{revision}, so a replay never duplicates.
  • Notifications map a subset to the existing toast pipeline (sendOsNotification), each behind its own NotificationSettings toggle, quiet until every source has been read once.
  • #88 subscribes to the same envelopes when it lands. Nothing here waits for it.

Retention

  • Runs at startup and every 6 hours. Deletes occurrences older than retentionDays, then the oldest beyond 20,000 per scope.
  • Protected: the newest occurrence of each group with a live claim, a fix PR waiting to merge, or a tracking issue. Those groups show "older history expired" instead of disappearing.
  • Groups with no occurrences, no claim and no decision are deleted. Decisions stay until you remove them. Claim events go with their claim.
  • Raw logs are never stored. Excerpts are capped at 2 KiB per signal and 20 signals per occurrence.

Account and repository boundaries

  • Every command takes a scope, and every query filters by it. A cross-repo suggestion compares scopes with the same host and account only.
  • A runtime restart (account or repo settings changed, see application-runtime.ts:29-58) bumps the generation. Queued work and late replies from the old generation are dropped.
  • A scope that leaves the settings is hidden at once and purged after 7 days, except protected groups, which show "repository no longer tracked".
  • maintenance::clear_cache keeps deleting only prcache.db. reset_all_settings deletes ci-failures.db as well, since a reset means starting over.

11. Sanitization and privacy

Sanitization runs in Rust before anything leaves the extraction command, so caching, rendering, copying and prompts all see the same scrubbed text. It is best effort and the UI never calls it a guarantee.

  • GitHub tokens (ghp_, gho_, ghu_, ghs_, ghr_, github_pat_), JWTs, Authorization: and Cookie: headers, Bearer values.
  • Credential query parameters (token, sig, se, X-Amz-Signature, X-Amz-Credential, code, password, secret), SAS tokens, user:pass@ in URLs.
  • Azure connection strings (AccountKey=, SharedAccessKey=), AWS key ids, PEM blocks, .npmrc _authToken.
  • Host paths: user home directories, runner temp roots.
  • GitHub's own *** masking is preserved.

The tokens BorgDock passes to ci_read_job_log are used for one request and never logged. A test asserts the Rust log output contains no token for a failing call. Content stays inside its scope. Copying a summary, sending evidence to an agent, or posting a tracking issue each show a preview first.

14. Verification

Unit tests (Vitest, pure modules)

  • Parameterized tests: same base, same message, different parameters group, with the variant listed.
  • Matrix: the same failure on node 18 and node 20 groups and lists both values. A different failure on each stays apart.
  • The same generic timeout with different causes stays apart. A catalog hit in different steps stays apart.
  • Retry attempts produce new occurrences. A pass on retry produces passed_on_retry and the flaky hypothesis.
  • Synthetic merge and merge_group SHAs: tested and head SHA tracked separately, outdated flag.
  • A changed assertion (Expected 200, Received 503 versus 404) produces two groups.
  • Normalization collisions: two different temp paths, the same test, an equal fingerprint. Two different well-known ports produce different fingerprints.
  • Fingerprint upgrade with majority mapping and ambiguous decisions. Manual merge and split, cannot-link beats high tier, medium links don't chain.
  • Ownership: lease expiry, staleness per owner kind, settled-thread prompt. The launch guard decision table.

Rust tests

  • log.rs against a local tokio test server: 302 then 206, 302 then 200 streamed past the cap, slow body timeout, 404, 410, 403, 429 with Retry-After, cancellation.
  • Parsers over the fixture logs ported from the TS tests, plus new fixtures per new parser.
  • Sanitizer table. A log-output test that no token appears.
  • Store: migration from empty, corrupt file moved aside, newer version read-only, retention protection, concurrent claims, account and scope purge.
  • bindings:check passes.

Fixture corpus

Collect 40 or more real failed job logs from FSP and BorgDock CI and sanitize them by hand. Label the pairs same cause or different cause. The corpus lives in src-tauri/src/ci_failures/fixtures/ and feeds the Rust extraction tests and the TS tier tests through a JSON export. A rule change that flips any labeled pair fails the build.

UI proof

  • Stories: confident match, uncertain candidate, generic only, evidence unavailable, truncated log, owned by a running thread, stale owner, launch failed, flaky, base branch, fix merged with PRs still red, cross-repo suggestion, empty.
  • Guard dialog, Investigate sheet, Rerun sheet (infrastructure and base-branch variants), Focus card, toolbar chip, settings card.
  • Capture each in dark, light and the narrow docked width with scripts/screenshot-stories.mjs, read every image, and fix what looks off before the PR is called done. Floating parts (dialog, sheets, menus) use --color-modal-bg, never --color-surface-raised.
  • Accessibility: the card is a labeled region, confidence is text and not only color, details toggles carry aria-expanded, and the dialog traps focus and returns it.

End to end

  • tests/e2e/ci-failures.spec.ts with mocked GitHub responses: two PRs with the same failure form a group, the filter shows both, Fix on the second warns once the first is claimed, and Launch anyway records an override.

17. Out of scope

  • Automatic reruns, skipping or overriding required checks, editing or updating PR branches, suppressing failures.
  • Matching across GitHub accounts or hosts.
  • Downloading logs from other CI systems (Azure Pipelines, CircleCI). Their check-run output and annotations are the evidence.
  • Distributed locking between machines beyond the GitHub tracking issue.
  • Backfilling history older than what BorgDock observes.
