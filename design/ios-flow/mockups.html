The flow

Today the walk starts on a file list, Approve moves on to another file list, and comments show as plain text. In the new flow you see what you need to judge a pull request before its files, every time you reach one you haven't read yet.

02

Focus: what waits on you, and what your agents are doing

Today becomes Focus, like the desktop. It leads with the review queue and the agents. Each agent is a row on its pull request: tapping the row opens the PR in BorgDock, the pill opens the thread in T3 Code. The sprint and work counts move below the pull requests.

03

Pull requests: every PR, grouped the way you want

The list drops the Needs you block that is pinned above every grouping. Your turn becomes a pill next to All, Mine, Failing and Ready. Groups fold, and BorgDock remembers which. Sorting gains Waiting longest and Smallest first. The server reads every repository the desktop watches, so a teammate's pull requests show up even when they don't involve you.

04

A pull request: checks, proof, description and comments on one page

The five tabs become one page with jump chips, so the description is a scroll away from the checks. A failing check shows the step and the error from its log, which the server already reads. The description and comments render as GitHub renders them: headings, lists, task lists, tables, code and folded <details>.

05

Review: straight into the first file, tests as one step

Start review opens the first source file directly; the "Walk 52 files" screen is gone. The navigation bar names the file and stays as you scroll down the diff. Files x of y moves under Mark reviewed. Tests and generated files come last, one step each, so a 52-file PR is 12 files to read and two steps to confirm.

06

After Approve: the next brief, the decision you made, and a load that recovers

Approve moves on at once and the approval waits out its five-second Undo. The next pull request opens on its brief, loaded in the background while you read the previous one. Going back shows what you decided. A PR that fails to load retries before it asks you anything.

07

Work: the states walk, made scannable

The Work tab keeps Dispatch's states walk: one lane per ADO state, a verdict on every item. Today every row is five lines tall and every lane is open, so 52 items are a long scroll. Rows become two lines, an item that needs nothing becomes one, and lanes fold to a summary. Lanes that need you open first. Scopes replace the separate Browse screen, and agents without an item open in T3.

08

A work item: the next step first, rich text intact

An item puts what decides the next step at the top: for a failed item that's QA's notes, in full. Rich text keeps its lists, tables and screenshots; today the server flattens it to plain text. Every linked pull request and agent is listed, the fields move below the text, and Activity joins comments and state changes, with a box to reply.

09

What's broken today, and why

Each problem you reported, traced to the code. "From the code" means the cause is plain in the source. "Likely" means the code explains the symptom, but it still needs a run on the device or the server log to confirm.

F1
Mark reviewed counts up, but the page shows the same fileLikely
Why
FileWalk is a paged TabView(selection: $session.fileIndex). markCurrentReviewed() jumps to the next unreviewed file, often several pages away, inside withAnimation. A paged TabView doesn't reliably follow a jump like that. The title reads fileIndex, so the count moves and the page stays. load() also sets fileIndex before the pager exists, which matches the walk starting at file 1.
Fix
Key the walk by file path, not position: a currentPath on ReviewSession and a horizontal ScrollView with .scrollTargetBehavior(.paging) and .scrollPosition(id:), or one FilePage with .id(path) and a swipe gesture. A UI test marks five files and checks that the page's file name matches the title each time.
F2
After Approve, the next PR doesn't load, then does a minute laterLikely
Why
ReviewSession.load gives up when the detail or the files fail, and offers only Skip. On the server, detail() reads up to four job logs of unread failing checks before it answers. With GitHub slow (the server log is full of timeouts reading base branches) that can pass the app's 30 s timeout. The next try is quick because the logs are read by then. detail and files both call recordOf at once, which can run the same GraphQL query twice.
Fix
Answer the detail without waiting for logs and let failure reasons arrive on the next read. In the app, retry once, then show Retry and Skip. Prefetch the next PR's detail and files while you review the current one, like the desktop's usePrefetchReviewSnapshot. Share one in-flight recordOf per PR.
F3
Back shows the approved PR's old stateFrom the code
Why
QuickReviewView keeps one ReviewSession per PR for as long as the review is open, and load takes the detail from FocusStore.details when it has one. The approval's onSent reloads Focus, never the detail.
Fix
The session records its decision (held, posted, failed) and the page shows it. onSent reads the detail again. Undo keeps working as it does now.
F4
The next PR opens on a file list; the first needs "Walk 52 files"From the code
Why
ReviewIntro shows the header, a re-review banner and up to 12 files left. The description and proof aren't on it. Every review starts there, so starting takes an extra tap.
Fix
A brief (description, proof, checks, what changed) for a PR you haven't opened in this session. Starting from the PR page opens the first source file directly.
F5
Comments and the description are hard to readFrom the code
Why
CommentBody and PrOverviewTab parse with AttributedString(markdown:) in inlineOnlyPreservingWhitespace mode. Headings, lists, tables and code blocks don't render, and HTML such as <details>, <img> and <!-- --> prints as text.
Fix
One GitHub markdown view for the description, comments and reviews. It builds on ChatMarkdown's block parser and adds task lists, HTML comments dropped, <details> folded, images moved to Proof, AB# chips, and the desktop's bot footer and badge rules.
F6
Needs you is pinned on top and can't foldFrom the code
Why
PrListQuery.groups adds a Needs you group above the others whenever the filter is All and the grouping is author or repository. Sections have no fold.
Fix
Drop the pin; Your turn is a pill. Groups fold and the folded ids are kept in @AppStorage. Add Waiting longest and Smallest first to the sort options.
F7
A teammate's 7 open PRs are missingFrom the code
Why
The server searches involves:@me, review-requested:@me and reviewed-by:@me, plus the repositories in github.repos. That list is empty in your server's config; the desktop watches 16. The repository search is also a single query capped at 100 results (5 pages of 20) and runs for the first account only.
Fix
The desktop link sends the desktop's repository list to the server. One search per repository, paged to the end, for the account that can read it. A footer in Settings says what was read and when.
F8
A T3 thread only opens from the Live ActivityFrom the code
Why
Threads show only inside work items, or on a PR that has no work item (PrOverviewTab shows "Agents on this branch" only when workItems is empty). They open BorgDock's copy of the conversation (ThreadView).
Fix
Agents on Focus and on every PR. The row opens the PR, and Open in T3 uses T3Link with the appLink the server already sends. The Live Activity opens the PR too. ThreadView goes.
W1
Work rows are five lines tall, and every lane is openFrom the code
Why
WalkRow draws AB# and the verdict, a two-line title, the workflow bar, a strip of evidence chips and the latest message for every item. Lanes can't fold, so 52 items are a long scroll.
Fix
Two lines per item, one when it needs nothing from you. Evidence moves to the second line. Lanes fold to a summary and open by default only when they need you.
W2
Browse is a separate screen, with no verdictsFrom the code
Why
The Work tab shows only your items. Anything else goes through the toolbar's BrowseView: a list in query order with its own look and no verdicts.
Fix
Scopes on the Work tab (Mine, the sprint, unassigned, Up next, saved ADO queries) in the same lanes, plus a search field for any AB#.
D1
Descriptions lose their lists, tables and screenshotsFrom the code
Why
The server's htmlToText flattens every rich-text field and comment to plain text before sending it, and the app's PlainText.clean strips what's left. Screenshots in repro steps disappear.
Fix
The server turns ADO's HTML into markdown (lists, tables, links, images) and proxies attachment images, since ADO needs your sign-in. The app renders it with the same markdown view as pull requests.
D2
An item shows one pull request and one agentFrom the code
Why
ItemDetailView shows entry.pullRequest and currentThread only. The desktop ranks every linked PR and marks the shared ones.
Fix
Every linked PR, the item's own first and shared ones marked. Every open thread, each with Open in T3.
D3
QA notes sit at the bottom; comments are hidden and read-onlyFrom the code
Why
Sections come in a fixed order with QA notes last. Comments show only when detail.comments.count > 1, there's no history, and nothing posts a comment.
Fix
The section that decides the next step leads: QA notes, the PR or the agent's question. Activity joins comments with state changes from the item's history, and a box posts a comment through a new server route.

Build order

Four pull requests, each usable on its own. The walk comes first because it's where the bugs are.

PR 2 · iOSReadable pull requests

F5 and the one-page PR: the GitHub markdown view for the description, comments and reviews, the proof row, failing checks with step and error on the page, jump chips.

PR 3 · server + iOSEvery pull request

F7 and F6: the desktop link shares its repositories, a search per repository paged past 100, the coverage footer. Your turn pill, folding groups, new sort options, Review all per author.

PR 4 · server + iOSFocus and agents

F8 and the server half of F2: Today becomes Focus, agent rows on Focus and every PR, Open in T3, the Live Activity opens the PR, ThreadView removed. The detail answers without waiting for job logs.
