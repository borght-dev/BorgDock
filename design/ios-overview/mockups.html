Today: where the overview goes missing

Pull requests shows mostly your own work, because the server never asks GitHub for review requests. Browse and Dispatch show the same 52 items. Browse lists them in query order with no verdicts. Dispatch has verdicts, but its first rule after the questions is the due date, and the whole sprint is past it. So nearly every row turns red, including the three QA sent back.

02

Focus: what to do, across everything

Focus is the home tab, so it gets the widest overview. Six tiles, each named for what you do: review, fix, merge, answer, rework failed QA, and the team queue. They cover pull requests, agents and work items. Under them, the one red main branch you should know about, then one ranked list across all of them.

03

Pull requests: every one that involves you

With the server fix (section 07) the tab gets review requests and the pull requests you reviewed, not only the ones you opened. On the work account that's 57 open instead of 18. Scopes split them by your relationship to each PR, the overview card splits them by repository, and team review requests get their own queue.

04

Dispatch: the overview first, failed QA on top

Dispatch opens on a card with one row per state, in the order you act on them: Testing Failed, Needs Human, Code Review, Development In Progress, New. Each row says what it holds in a few words. Tap one to jump to its lane. The lanes below use the same order, and a jump bar stays under the nav bar while you scroll.

05

Queries as scopes

A saved ADO query opens in the same view as Mine, with the overview card, the lanes and the verdicts. Items that aren't yours have no threads or pull requests on the server, so their verdict comes from the state alone. They show who has them instead of "You". Pin the queries you use; pinned scopes show their counts and how many failed QA.

06

A failed item: what QA saw, and the fix one tap away

The item screen for a Testing Failed item puts QA's notes first, in full, above the description. A short history shows how it got here: when it went to QA, which pull request took it there and how often it came back.

07

What it takes

The server fix for missing pull requests is done and tested in this change. Rule step 1 is next: small, and it fixes the badge and the hidden failed items on the phone and the desktop. The rest builds on those two.

Done · serverReview requests arrive

  • Three searches per account: involves:@me, review-requested:@me (you and your teams) and reviewed-by:@me.
  • Each is its own request, 20 per page, up to 100. All three in one query made GitHub time out (504).
  • A search that fails keeps its last answer, and the account says which one.
  • Live: 57 open on the work account instead of 18, 4 rate-limit points per poll.

2 · Focus and PRsTiles, scopes, team queue

  • A Team bucket for requests that reach you only through a team (isWaitingOnMe already tells them apart).
  • Focus tiles from the bucket counts plus Dispatch's briefing; Up first ranks across both.
  • PR scopes and the repository card are computed in the app from PrSummary.

1 · Dispatch rulesFailed QA outranks Overdue

  • verdict.ts and the server's port: Testing Failed gives "Failed QA" (was "Bounced back") and runs before the due-date rule.
  • A late due date leaves the verdicts and becomes an evidence chip, "9 d late".
  • The briefing and the tab badge count failed QA, Needs Human and agent questions.
  • Spec table in 2026-10-13-dispatch-state-walk.md changes with it.

3 · ADO dataWho, when, how often

  • Microsoft.VSTS.Common.StateChangeDate in ITEM_FIELDS: "since when" for every row, from the batch call it already makes.
  • For Testing Failed items only: workItems/{id}/updates for who moved it and the round count, and Custom.QANotes. Cached on System.ChangedDate, like comments.

4 · ScopesBrowse becomes a scope

  • The server runs the walk over a query's items. Items that aren't yours get state-only verdicts.
  • Pinned scopes are stored per account. The ADO poll refreshes their counts (WIQL ids, then System.State in one batch).
  • OverviewView takes a scope. BrowseView and its strips go away.

5 · RowsDense and swipeable

  • Three row kinds: failed (QA quote and Fix), full (a verdict that asks something) and one line for the rest.
  • Swipe actions and a context menu replace the Queue and Start buttons.
  • The jump bar and lane sorting.

Decisions for you

  • Team review requests. Today a request to your team counts as Needs you, on the desktop too. With 39 of them, Needs you is mostly team work. Give them their own Team bucket, as mocked, or keep them in Needs you?
  • Teammates' PRs that don't ask you. The GitHub app's Pull requests screen lists created, assigned, mentioned and review requested, which the new searches cover. Every open PR in a repository, as the desktop shows, needs github.repos in the server's config.json. It's empty now. Which repositories?
  • Lane order. The mockups put Testing Failed and Needs Human first. The desktop's WALK_ORDER starts with Code Review, the order of the morning routine. Change both, or only the phone?
  • Is "Assigned for me" the same as Mine? Mine is every open item assigned to @Me, in every project. If your query filters more (area path, type), keep it as a scope of its own.
  • What counts as failed QA. Only the Testing Failed state, or also items QA moved straight back to Development In Progress? The second needs the updates call for every item, not just a few.
  • Overdue. Drop it from the verdicts for good, or keep it while the sprint is still running and drop it once the sprint has ended?
