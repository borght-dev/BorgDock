BorgDock for iPhone

Concept mockups. BorgDock's server watches your pull requests, work items and agents around the clock, so the phone works on its own: a review to give, an agent waiting for an answer, a red master, and what changed while you were out. The desktop app is optional.

Answer, don't browseA phone session lasts thirty seconds. Every screen opens on what needs you and puts the one action under your thumb.
The same rules as the desktopFocus buckets, Dispatch verdicts, the Activity journal and CI fingerprints are one TypeScript package that the desktop and BorgDock's server both run, so the phone never disagrees with the dock.
Agents stay on your machinesThe phone steers T3 threads on your Mac mini, workstation or build VM through a small connector on each. No VPN on the phone, and the phone never runs code.
Nothing final without a beatApprovals keep the Undo countdown, merges show their checks and ask for Face ID, and ADO moves go through an agent run, as on the desktop.

01

Focus: what needs you, first

The home tab is the desktop's Focus board as one column. The four buckets (Needs you, Waiting on others, Ready to merge, Stale) become a pill strip; each card says why it is yours in one line. Agents waiting on you sit under the pull requests, since an answer from you often unblocks more than a review does.

02

A pull request, on one screen

The PR detail keeps the desktop's tabs (Overview, Files, Checks, Proof, Comments) as a scrolling strip. The header answers the three questions you have on a phone: is it green, does it conflict, which work item is it. The bottom bar holds the next step: start the review, or hand the failure to an agent.

03

Quick Review, one file per swipe

The desktop's file walk fits a phone well: one file at a time, unified diff, mark it reviewed and swipe to the next. Approve stays locked until every file is seen, the decision appears after the last one, and an approval waits out its Undo before GitHub hears about it.

04

Dispatch: your work items and the agents on them

Dispatch's States view is the morning walk: one section per ADO state, each item with a verdict, its evidence and the latest message. On the phone the main job is answering agents (approve a plan, pick an option, nudge a quiet thread) and starting new ones on a machine at home or in the office.

05

Activity, notifications and widgets

The Activity journal is the phone's inbox: what changed since you last looked, kept until you read it. The server keeps the journal with the desktop's rules and drains its outbox to APNs, so a burst becomes one summary, nothing pops twice, and an entry you read on any device clears everywhere. Widgets and Live Activities answer "do I need to look?" without opening the app.

06

Notes and search

The phone is where thoughts arrive: on a walk, in a meeting, right after a call. Notes opens on today's daily note with what happened since yesterday already written in, and a quick note is one press of the Action button away. Search reaches everything BorgDock knows by number or by word.

07

Workstreams and related CI failures

Two read-mostly screens for the bigger picture. A workstream shows a goal, the outcomes it needs and the live evidence behind each one. A CI failure group shows one failure across master and every PR it hits, who claimed it, and what a rerun will and won't fix.

08

Account and setup, no desktop needed

The phone works on its own. You sign in with a BorgDock account (Clerk), BorgDock's server reads GitHub and Azure DevOps for you, and each machine that runs T3 joins by running a small connector. The desktop app is optional: sign it in to the same account and it shares read state and tells the server when you're at your desk.

09

How it would work

BorgDock grows the Dispatch project into its backend (now src/BorgDock.Server in this repository). Dispatch already runs the hard parts every day: an always-on server reachable without Tailscale, APNs pushes that answer agent questions from the lock screen, the T3 protocol 2 fleet with offline snapshots, and a tested SwiftUI app. BorgDock brings its rules, its GitHub side and its design.

RecommendationGrow Dispatch into BorgDock's backend

Most of the risky work is already done and running: an internet-reachable server with a careful security model, APNs with lock-screen answers, the T3 fleet and a SwiftUI app with 81 unit tests. Rebuilding that in Tauri would cost more than restyling it. The rules stay single-sourced because the server is TypeScript too.

What changes in Dispatch: Clerk replaces its own passkey and setup-code sign-in (the physical-access rule moves to adding a machine), BorgDock 4.9's fresh worktrees replace the M/V/W slots, GitHub polling joins ADO and T3, and the app takes BorgDock's tokens instead of paper and teal.

SecurityA session can start agents

Dispatch's security note holds for BorgDock too: a signed-in session can start full-access agents, so a stolen session is remote code execution. The design keeps three locks:

  • Sign-in through Clerk with a passkey, Apple, GitHub or Microsoft. No passwords.
  • Machines join from the machine. The connector prints the code; it works once, for two minutes.
  • Agent commands are signed on the phone. Start, answer and approve need Face ID and a Secure Enclave key the connector trusts. The server relays them but can't forge one.

SettledFrom your answers

  • Independent of the desktop: the server watches and pushes; you sign in with a Clerk account.
  • No Tailscale on the phone: the server is public (Funnel now, your own domain later); only connectors talk to T3.
  • Rate limits: the server reads each account once for all your devices; once the desktop reads from the server too, nothing polls twice.
  • Distribution: TestFlight now (Dispatch has deploy/testflight.sh), the App Store when BorgDock goes public. App Review expects Sign in with Apple next to GitHub and Microsoft; Clerk has it.

Still open

  • Where the server lives after phase 0. The Mac mini (one user, free, data stays home) or hosted (anyone can sign up; needs per-user isolation and the connector split for everyone, not just you).
  • Work tenants. An Enterprise Managed GitHub account may block third-party OAuth apps, and Entra may need admin consent for the Azure DevOps scope. The machine route (gh, az) covers both; test the account route early.
  • Clerk as a dependency. Sign-in then needs Clerk to be up, where Dispatch's own passkeys needed nothing. Clerk's session tokens live about a minute, so the server should trade a Clerk sign-in for its own device session (Dispatch's 180-day app token); then an outage only blocks new sign-ins.
