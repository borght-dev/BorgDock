BorgDock · design study · 12 Nov 2026

Work item: full view, peek and hover card

One model of the work item drives all three surfaces, and that model comes from the Azure DevOps form layout instead of a hard-coded list of fields. Every type keeps its own pages, groups and custom fields. BorgDock adds only what ADO can't: the gist, the pull request and agent around the item, and what to do next. Sample data is made up (AB#4127, Northwind Foods).

What the current screens get wrong
01 · repeatedEvery fact shows up twice

State, priority, assignee and iteration sit in the header pickers and again under Properties. In the peek, the type shows three times.

02 · rigidThe rail ignores the ADO form

Properties / People / Planning are hard-coded. Custom groups and fields end up in a "Custom Fields" grid or don't show at all, and type and state colours come from a fixed map.

03 · buriedStatus is below the fold

The newest Developer Notes update, the linked PR and the agent's state are a scroll away. The screen opens on an email disclaimer.

04 · noiseEmail clutter fills the screen

External-sender banners, signatures, phone numbers and cid: images that can never load show up as empty frames with lots of whitespace.

05 · crampedA 35-comment thread in a 240 px rail

Vera's long comments, with proof hashes and file paths, overflow sideways. Meanwhile the Activity tab says "coming soon".

06 · overflowLines run 1,600 px wide and scroll sideways

Text has no maximum width, and long hashes and URLs force a horizontal scrollbar in both the full view and the peek.

07 · hoverThe card shows the disclaimer

Its excerpt is the first text in the description ("CAUTION: This email originated…"), and its footer hints wrap onto three lines.

keptWhat already works

Auto-save, inline pickers, AB# links, the type stripe on the card, PR and T3 chips on the card, and tabs built from custom pages.

Decided · 12 Nov
Header fact by ruleThe type's own header fact is the first field it has from Severity, Effort, Story Points or a due date. No per-type setting.
Discussion moves to ActivityOnly the latest message matters day to day. It surfaces in Latest, and the full thread lives in the Activity tab.
The card always shows what it's aboutThe hover card always shows the description, or the repro steps when a Bug has none. The latest update is one line under it.
A

Full view: Details

The header answers "what is this, and where does it stand?". The tab answers "what does it say?". Each fact has one place, and you edit it there. The rail lists only what isn't in the header, grouped the way the team's ADO process groups it.

  1. 1Fact strip. State, Assigned To, Priority and Iteration, plus the type's own key field (Severity for a Bug). You edit them here and nowhere else.
  2. 2Now. The linked PR with its checks and conflicts, the T3 thread, and the next step from Dispatch's verdict.
  3. 3Latest. The newest of: the top Developer Notes entry, a comment, or the agent's last message. It's the same rule as Dispatch's latestMessage.
  4. 4Noise folds. The external-sender banner, the signature and email inline images collapse to one line each. Show brings back the original.
  5. 5Rail from the layout. ADO's group names and order. Fields already in the header are skipped, and empty fields fold into "2 empty".
  6. 6Custom pages are tabs. "Autoship" is a page in this process's Bug layout. Empty long-text fields from the layout are offered as "+ Add".

The ADO form layout drives the screen

ADO describes every work item type as pages, then sections, then groups, then controls. BorgDock already reads that layout (services/ado/layout.ts) but keeps only field keys per page. Keeping the sections, groups, labels and control types is enough for the rules below to place any field on any type, including custom types and fields nobody has added yet.

Rules
  1. 1
    A fixed set of header facts, plus one from the type

    State, Assigned To, Priority and Iteration are always facts. On top of those comes the first field the type has from Severity, Effort, Story Points or a due date. The rail then skips every field that's a fact.

  2. 2
    Pages become tabs

    The first custom page is Details. Later ones (Autoship) follow the system tabs, and empty pages are hidden. History, Links and Attachments keep BorgDock's own tabs.

  3. 3
    Long-text fields in section 1 go in the main column, in layout order

    Dated, append-style fields (Developer Notes) feed Latest and show as a log. An empty field becomes "+ Add". Plain fields in section 1 show as a compact grid below the long text.

  4. 4
    Groups become rail groups

    ADO's label and order, including custom groups. A layout label replaces the field name. Read-only fields show a lock, fields required for the next state show a dot, and empty fields fold away.

  5. 5
    Known controls are drawn natively

    Development shows the PR, branch and commits with live checks. Related Work shows parent, children and related items, and children get a progress bar.

  6. 6
    Every other control gets a row

    An extension BorgDock can't render becomes "Open in ADO" in its group. Nothing in the layout disappears without a trace.

E

Hover cards

The card answers "what is it about and where does it stand?" in a glance. The description is always there, because that's where you learn what the item is. The newest update sits on one line below it. Its facts follow the same header rule as the full view, so they change by type.

  1. 1Always the description. It falls back to Repro Steps when a Bug has no description, and to the first long-text field for other types. The banner, greeting and signature are removed first. Three lines at most.
  2. 2Latest in one line. The newest Developer Notes entry, comment or agent message, the same pick as Latest in the full view. It's left out when there's none.
  3. 3Facts by type. Severity on a Bug, Effort on a PBI, a due date on a custom type, with at most four.
  4. 4One-line footer. Who changed it last on the left and short hints on the right. It never wraps.

Rules & build notes

Noise rules and field renderers are pure functions, shared by the long-text blocks, the peek and the card's gist. Each rule only folds content. Show restores the original, and Edit always edits the original HTML.

Noise rules

Applied to HTML fields before rendering and before the gist is taken.

NoiseDetected byShown as
External-sender bannerFirst block mentioning "originated from outside", "CAUTION:" or "[EXTERNAL]"One-line fold
SignatureBlocks after a sign-off line (regards, groeten, cordialement…) with name, title, phone and address linesFold naming the sender
Email inline imagessrc="cid:…", or an image that failed to load after the auth retryCounted in the fold, never an empty frame
Logos and trackersImages ≤ 48 px, or three or more images in the signature blockCounted in the fold
Blank runs<p>&nbsp;</p> runs and stacked <br>One paragraph gap
Long tokensHashes, paths, URLsWrap anywhere. Bare URLs become link chips

Field renderers

Chosen by the field's ADO type, so a custom field gets the same treatment as a built-in one.

ADO typeRendered as
htmlReading block (Instrument Sans 14.5 px, max 860 px wide), clamped after ~14 lines with "Show all · N words"
plainTextPre-wrapped text with the same clamp
string / picklistInline value. A picklist opens a menu of the allowed values
identityAvatar and name. "Assign me" when the field is empty and it's Assigned To
treePathLast segment in full, parents muted, full path in a tooltip
dateTime"Fri 14 Nov · in 2 d", red once overdue
integer / doubleTabular figures with grouped thousands
booleanToggle
contributionNative when known (Development, Related Work). Otherwise "Open in ADO"

Where it lands in code

  1. services/ado/layout.ts: normalizeLayout keeps sections, groups, labels, read-only flags and control types instead of only field keys per page.
  2. New pure services/ado/form-model.ts: layout, fields and type metadata go in, and { facts, tabs: [{ main, rail }] } comes out. The full view, the peek and the card all read it.
  3. RightRail.tsx (hard-coded Properties / People / Planning) becomes a LayoutRail driven by groups. The "Custom Fields" grid in OverviewTab goes away.
  4. Type and state metadata (/workitemtypes, /states: colour, icon, category) replace the WI_TYPES / WI_STATES maps, which stay as the offline fallback.
  5. The ActivityTab.tsx stub becomes a timeline built from workItems/{id}/updates plus comments. Vera's runs are grouped by the Vera · <kind> — prefix Dispatch already reads.
  6. workItemPeekOf keeps the description (Repro Steps for a Bug without one, else the layout's first long-text field), cleaned by a pure html-noise.ts. It gains latest from Dispatch's latestMessage (verdict.ts), which also feeds Latest in the full view.
