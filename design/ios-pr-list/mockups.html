Pull requests on iPhone, the way the desktop does them

Concept mockups for the Pull requests tab and Quick Review. The phone gets the desktop's filters, groupings, orders and saved views, and its end card that offers the next pull request. A filter is the same query string on both (repo:shop -checks:failing author:priya), so a view means the same thing everywhere.

One query, both appsThe filter is the desktop's query string. Chips show its qualifiers, the Filter sheet writes them, and typing author: in search does the same.
Every desktop groupingEleven groupings instead of four, a second level (Then by), and five orders that each run either way.
You pick the next PRA finished review offers the same author's next pull request or the next one by priority, as the desktop's end card does.

01

The list: filters as chips, groups inside groups

Tabs stay where they are and gain Stale, the desktop's sixth tab. Under them sits a chip row: Filter (with how many filters are on), then one chip per filter. The bar under the chips names the grouping and the order, and opens Display. Grouped by status, the groups are the desktop's five: Your turn, Failing, Waiting for review, Ready to merge and Draft.

02

Filter: every field the desktop filters on, values with counts

The desktop's Filter menu as a sheet. Fields come in the desktop's order. A field you set shows its values in place of "Any". A field opens its values, each with how many PRs it matches within your other filters. Is and Is not switch between keeping and leaving out. Picking several values matches any of them.

03

Display: every grouping and order from the desktop

Eleven groupings don't fit a segmented control, so Group by, Then by and Order by become menu rows. Orders are the desktop's five, each with a direction. Today's Waiting longest is Created, oldest first. Smallest first is Size, smallest first. The switches are the desktop's group switches plus Dependency updates as one group, which only the phone has.

04

Saved views: a tab that remembers its filters and display

Save view keeps the tab, the query and the display under a name. It becomes a pill after the built-in tabs, with its own count. Change anything while a view is open and a bar offers Update view or Save as new, as the desktop does. Leaving the view for a built-in tab brings back that tab's own display.

05

Quick Review: you choose what comes next

Review on a pull request reviews that pull request alone, as on the desktop. Today the phone carries on into the rest of Focus's queue. When the review is done, the desktop's end card offers what's next: the same author's next pull request, or the next one by priority from someone else. Long-press gets the desktop's author run, "Review Priya Shah's PRs, oldest first". Focus's Start review still runs the whole queue.

07

Build and open questions

Two pull requests. The list on feat/ios-pr-sort-group-filter in three parts, then Quick Review. The Swift model ports the desktop's pure functions one to one, and its tests reuse the desktop tests' query strings, so the two can't drift without a test noticing.

ServerWho was asked, who answered

PrSummary gains requestedReviewers, requestedTeams and a review status that includes commented. focus.ts reads all three from GitHub already; it only stops dropping them. Shared type, fixtures and Swift model follow.

iOS modelThe desktop's list in Swift

PrListQuery grows into the desktop's model: facts (five buckets, review state, waiting on, age, size), the query parser with setTerm / removeTerm, facet values with counts, eleven groupings with Then by, five orders with a direction, saved views. Stored display choices migrate.

iOS screensChips, Filter, Display, views

The chip row and match bar, search tokens and suggestions, the Filter sheet and its value lists, the new Display sheet, view pills with Update / Save as new, and the Save view sheet. Unit tests, plus UI tests and screenshots under BorgDockVisual.

iOS, second PRQuick Review's next

Review on a PR reviews it alone. The end card: counts, decisions, left out, Next from the author (the desktop's nextFromAuthor), Review next by priority, Done. The author run on long-press and Walk through on your own PRs.

Open questionsYours to decide

  • Saved views from the desktop. The mockup keeps views on the phone. The desktop link already shares the repositories; it could share saved views the same way, read-only on the phone. Phone only for now, or both?
  • Phone-only extras. The Waiting tab and Dependency updates as one group have no desktop counterpart. The mockup keeps both. Keep, or drop them for strict parity?
  • E2E reports and shared CI failures. The desktop clears a red pull request when the E2E report or a shared failure shows it isn't the PR's doing; the phone can't tell. Read them on the server so the phone's runs match, or leave red PRs out on the phone?
  • Default display. The desktop starts grouped by status, by priority. The phone starts by author, waiting longest. New installs follow the desktop, or keep the phone's default?
